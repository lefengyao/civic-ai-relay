# 2026-09-25

## 线上故障：流式对话「突然中断」——根因是上游客户端的总超时（340 秒）

**现象**（老板报）：对话突然中断，怀疑"达到峰值"；他给模型的单价都是 0。
部署环境：阿里云 ECS + 宝塔 + Docker Compose，前面 **Nginx**。

**先排除的**（从他服务器拉的数据）：
- 额度：`TOKEN_LIMIT_*` 与 `AMOUNT_LIMIT_*` **全是 0（不限）** → 不是额度。单价 0 只影响金额维度，
  但这台连 token 维度也是不限。
- 内存：容器 `7.98MiB / 256MiB` → 不是 `MEMORY_LIMIT_MB` 保护。
- 并发/RPM：`active=0`、`rpm.used=0`。
- 请求分布：43 completed / 6 failed / 1 aborted。

**决定性证据**：失败请求里有一条
`created 13:54:31.404 → finished 14:00:11.411 = **340.0 秒**`，
且 `upstream_status=200`（响应头已收到）、`input/output_tokens=0`（流没走完，收不到 usage）。

**根因**：`internal/upstream/client.go` 从项目第一个提交起就是
```go
http: &http.Client{Transport: transport, Timeout: connect + read + write}
```
`http.Client.Timeout` 是**整个请求的总超时，含读取响应体的全部时间**。默认
`10 + 300 + 30 = 340 秒` → **任何超过 340 秒的流式对话必然被无声掐断**。
同时 `MAX_STREAM_DURATION`（默认 30 分钟，管理台可配）**从来没作用到请求上**，
只被后台回收循环当作「多久没结算算陈旧」的阈值 —— 两个数字互相矛盾，实际生效的是 340 秒，
而且它不出现在任何配置项里（是三个配置相加的结果），运维根本无法察觉。

**修复（v0.3.7）**
1. `upstream/client.go`：`http.Client.Timeout` 改为**不设**（0）。职责拆分：
   「上游不响应」→ `Transport.ResponseHeaderTimeout`（connect+read，默认 310s）；
   「流跑太久」→ relay 层用 context 施加 `MAX_STREAM_DURATION`；
   「客户端断开」→ 请求自己的 ctx。
2. `relay/service.go`：新增 `requestContext()`（`>0` 用 `WithTimeout`，`<=0` 表示**不限**，
   与其它配置「0 = 不限」口径一致），流式与非流式都套上；新增 `cancelOnClose` 把 cancel
   绑到 `response.Body.Close()` 上（调用方本来就会 defer Close，不会漏 timer）。
   失败分支用**原始 ctx** 结算，避免 upstreamCtx 已超时导致落库失败、预留只能靠 reaper 兜底。
3. 测试：`upstream/client_test.go::TestClientHasNoAggregateTimeout`（白盒钉住 Timeout==0 且
   ResponseHeaderTimeout 保留）、`TestStreamSurvivesPastAggregateTimeoutBudget`（每 120ms 一帧共 5 帧、
   而 connect+read+write 只有 400ms —— 旧实现会在第 3 帧后掐断，现在必须读完）；
   `relay/service_test.go::TestRequestContextAppliesMaxStreamDuration`。

**排查手法留档**：先看 `/admin/api/overview` 的 `recent` 里每条请求的
**created→finished 时长**与 `upstream_status`/token 数——
`upstream_status=200 + 零 token + 固定时长`= 被超时掐断，而不是被守门拒绝或上游拒绝。

## 另一条待办：Nginx 缺 `proxy_buffering off`
他那台 `nginx -T | grep proxy_` 的结果里**没有 `proxy_buffering`** → 默认 `on`，
流式响应会被 Nginx 缓冲（表现为"发出去没反应/一次全蹦出来"）。
已有 `proxy_read_timeout 600s`、`proxy_http_version 1.1`、`client_max_body_size 50m`。
建议补 `proxy_buffering off;`（配置片段见 `docs/client-integration.md` 第八节）。

都配成 `1s`（聚合 3 秒 < 流时长 6 秒），新旧镜像各跑一次 ——

| | v0.3.6（旧） | v0.3.7（修复） |

| 耗时 | **3.0s**（恰好在聚合超时处被掐） | 5.0s（跑完整条流） |
| 收到帧 | **3 帧**（应 6 帧） | 7 帧（6 内容 + 1 usage 尾帧） |
| `[DONE]` | **没有** | 有 |
| 记账 | **failed**（upstream=200，in/out=0/4） | **completed** |

旧版三条断言失败、新版 **13/13** —— 线上症状被完整复现并修复。
其余回归：`go test ./...` 全绿、`run_client_onboarding.py` 48/48、`run_e2e.py` 66/66。

**顺带堵的坑**：`UPSTREAM_*_TIMEOUT` 改了要**重启容器**才生效（启动时按值交给 Registry），
但 `RestartOnlyChanges` 里只有 HOST/PORT/DB_PATH → 管理台显示「已即时生效」，
运维会以为调大了超时。已补进 `RestartOnlyChanges`（后端回 `pending_restart_fields`，管理台提示重启）。
