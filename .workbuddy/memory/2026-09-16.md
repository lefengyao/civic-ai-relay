## 排查：服务器上加「本地模型渠道」一直弹 provider_invalid

- 症状：管理台「编辑供应商」保存后弹 `provider_invalid`（截图里连续 9 个 toast），上游地址填的是 `127.0.0.1:6000`。
- 根因：`internal/store/providers.go` 的 `validateProviderURL` 用 `url.Parse`，无 scheme 的 `127.0.0.1:6000` 直接解析失败（Go 原生报 `first path segment in URL cannot contain colon`），落到 "must be an absolute URL…" 分支 → `admin.go:269` 回 400 `provider_invalid`。**必须写全 `http://` 或 `https://`**。
- 复刻该校验函数实测（临时目录 `_urlcheck/` 已删除，未改任何仓库代码）：
  - **拒绝**：任何缺 scheme 的写法、`http://host.docker.internal:6000`、`http://<容器名或服务名>:6000`、`http://0.0.0.0:6000`、`http://8.8.8.8:6000`、非本地的 HTTP 域名。
  - **放行**：`http(s)://127.0.0.1`、`http://[::1]`、`http://localhost`、`http://*.localhost`、`http://*.test`、私有 IP（10./172.16-31./192.168.）、以及任意 `https://`。
  - 存库时会剥掉尾部 `/` 与 `/v1`（所以地址框不用带 `/v1`）。
- 关键推论：**`host.docker.internal` 与同 compose 网络的服务名都不在放行名单**。容器访问宿主机上的服务只能：用网桥网关 IP（默认 bridge `172.17.0.1`，compose 自建网络一般 `172.18.0.1`，用 `docker network inspect` 确认）或宿主机内网 IP，**且上游服务必须绑 `0.0.0.0`**；用 `127.0.0.1` 只会指到容器自己。
- 已知缺陷（当日晚些时候已修复，见文末；本条保留原始诊断记录）：provider 建/改失败时统一回 `provider_invalid`，真实 `err` 被丢弃，管理台只看到一串无信息量的 toast；前端 `base_url` input 也没有 `type="url"` 做前置校验。

### 遗留
镜像需用户自行 rebuild 部署，未能在其服务器实机复现。若 rebuild 后仍报错，新 toast 会直接给出原因；另给了零重建的二分法：用 `https://api.openai.com` + 同一名称/Key 提交，成功=地址问题，失败=重名或加密密钥问题。

### 环境踩坑（沙箱）
- **PowerShell `Remove-Item` 删工作区文件不生效**（返回 exit 0 但文件仍在，`-Force`/`-LiteralPath` 都不行）。改用 node `fs.unlinkSync` 一次删净。
- PowerShell 用 `>` 重定向输出是 UTF-16LE，Read 工具会判成 binary；一律用 `| Out-File -Encoding utf8`。
- `docker.exe` 把进度写 stderr，导致 PowerShell 判定 exit code 1，即使构建成功。判断成败要看输出里的 `naming to ... done`。
- 本次会话 Bash 工具整体不可用（shim 坏掉，连 `ls`/`cat` 都 `command not found`），全程改走 PowerShell + Out-File + Read。

## v0.3.2：配额模型重做 + 前端体验 + 端到端联调 + 发布打包

用户诉求：优化体验与 token 计算、消灭「明明还有余量却提示无法使用」；随后追加：**可以先欠费，
发现欠费再停服**（token 与金额都算）；**5 小时窗口从只有 token 扩展为也支持金额**，并加**日、周**维度，
**都可选择不限**。

### 根因（不只是 token 估算）
1. **额度拒绝返回 500**：`public.go::writeServiceError` 的 switch 没有 `QuotaError` 分支，落到 default 返回
   `500 relay_error`，客户端当服务端故障反复重试。
2. **预留口径过于悲观**：要求 `窗口已用 + (输入估算 + 输出上限) <= 限额`，窗口还剩一点但不够整个输出上限就整体拒。
3. **Key 被额度自动永久停用**：`finishRequest` 把 Key 置 `enabled=0`，调大限额也不恢复 → 典型的"还有余量却用不了"。
4. **出厂默认就是坑**：引导模板 `GenerateInitialSettings` 写死 `TOKEN_LIMIT_5H=100000`/`DAILY=20000`，
   新部署第一次编码类请求必被拒。

### 改动
- `internal/config/settings.go`：新增 `TokenLimitWeekly` / `AmountLimit5H|Daily|Weekly`（金额配置单位**元**，
  内部微元；`amountLimit`/`formatAmount` 负责换算），既有 5h/日 解析改为「0 或空 = 不限」；`TokenLimits()`/`AmountLimits()` 便利方法。
- `internal/config/store.go`：引导模板六个额度项全部写 `"0"`。
- `internal/store/ledger.go`：新增 `QuotaLimits`（6 项 + RPM）与带明细的 `QuotaError`（Scope/Metric/Used/Limit + `Detail()` 中文说明）；
  `ReserveRequest` 改为**先欠费后停服**（`used >= limit` 才拒，6 个维度各一次查询，同时取 tokens 与微元）；
  新增 `billingWeekStart`（北京时间自然周，用区间查询避免加列/迁移）；`estimateInputTokens` 加 `perRequestOverheadTokens=4`；
  `Overview`/`GroupOverview` 返回 weekly 与微元；**删除结算时的 Key 自动停用**。
- `internal/store/keys.go`：**删除只被测试引用的第二套配额实现** `ReserveForKey`/`SettleKey`/`KeyReservation`。
- `internal/store/schema.go`：迁移 v9，把历史 `disabled_reason='quota_exhausted'` 的 Key 恢复启用。
- `internal/relay/service.go`：透传 6 项限额；把 `tools`/`functions`/`response_format` 计入输入估算；兜底 settings 不再带死额度。
- `internal/httpapi/public.go`：`QuotaError` → **429 + 具体 code + 中文明细**（chat 与 responses 两个端点共用）。
- `internal/httpapi/admin.go`：`Overview` 传新限额。
- `web/admin.html`：概览改为 5h/日/周三张额度卡（每张同时显示 Token 与金额，0 显示「不限」，用满标红提示「已欠费」）；
  Key 列表加欠费标记；新增 4 个配置项标签并标注金额单位与「0 = 不限」。
- 文档：README 配额小节重写、`docs/admin-api.md` 新增「额度模型与错误码」、新增 `docs/DEPLOY.md` 模板。

## 补：面向 Ubuntu 的部署支持

用户告知服务器是 **Ubuntu + 已装 Docker**，要具体步骤。顺着发现两个必须处理的现实问题：

1. **Ubuntu 用 apt 装的 `docker.io` 常常不带 Compose v2 插件**（`docker compose` 不存在）→ 在
   `docker-ops.sh` 的 `require_engine` 里加检测并提示 `sudo apt install -y docker-compose-v2`。
2. **compose 项目名 = 目录名**，而发布包解压出来的目录叫 `civic-relay-v0.3.2`，与用户原部署目录名不同。
   在新目录里 `up -d` 会新建空卷 → 表现为「配置全没了要重新取管理员密钥」，而旧卷其实没删。
   这是**升级路径上最容易造成误判成"数据丢了"的坑**，已写进 `docs/DEPLOY.md` 第五节并加显式警告。

改动：
- `scripts/docker-ops.sh`：新增 `检查环境`（doctor，含上述两个检查 + 端口占用 + ufw 放行 + 直接判定
  「全新安装 / 升级」）、`载入镜像 [文件]`（`docker load` gzip 镜像包，默认当前目录 glob）、
  `启动离线`（不带 `--build` 的 up）；修正帮助里 `CIVIC_RELAY_BIND` 默认值的错误描述（应为 `0.0.0.0`）。
- `docs/DEPLOY.md` 模板：加「零、Ubuntu 前置检查」与「⚠️ 升级必须在原部署目录里做」两节。
- 验证：`bash -n` 通过并实跑 `检查环境`/`帮助` 全部分支（沙箱 Git Bash 缺 coreutils，只能冒烟）；
  三个关键文件确认是 LF 换行（CRLF=0），否则 Ubuntu 上会报 `bash\r: No such file or directory`。
- 已重新打包（v0.3.2 三个 tar.gz + SHA256SUMS.txt 全部更新）。

## 修：docker-ops.sh 把卷名与容器名写死了

用户按建议装到 `/opt/civic-relay` 后问「如何查看密钥」，顺带发现：脚本顶部硬编码

```bash
CONTAINER="civic-ai-relay-civic-relay-1"
CONFIG_VOLUME="civic-ai-relay_civic-relay-config"
DATA_VOLUME="civic-ai-relay_civic-relay-data"
```

只在「部署目录名恰好是 `civic-ai-relay`」时成立。目录一改名（我恰恰建议了 `/opt/civic-relay`），
`管理员密钥` / `删密钥` / `看卷` / `备份` / `恢复` / `探针` 全都会报「找不到卷」。
已改成按当前目录推导：`project_name()` / `config_volume()` / `data_volume()`，
容器用 `docker compose ps -q civic-relay` 解析 ID（`require_container()` 带找不到时的提示）。
另外 `升级` 命令现在先看本地有没有对应 tag：有就直接 `up -d --force-recreate`（不构建），
没有才提示去 `载入镜像`——之前的实现无条件 `--build`，离线服务器上必然失败。
`管理员密钥` 也改成：一次性文件不在时自动回落到从 `relay.env` 里 grep `ADMIN_API_KEY`。

教训：**运维脚本里凡是带项目名前缀的 Docker 对象名，都必须从当前目录/compose 推导，不能硬编码。**
