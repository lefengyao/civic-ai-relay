## v0.7.2 — 额度账本独立于主数据，删 Key / 模型不再把用量清零

**当时存在的问题**

v0.7.1 修掉了「周期用满后交接到周窗口」那一条归零路径，但还有两条会让人看到「周期额度从 0 重新计」：

1. `key_reservations.key_id` / `model_id` 带 `ON DELETE CASCADE`。额度是按 `group_id` 统计的，所以**删一把 Key（或删模型、删渠道）会把该组这一段的账目整段删掉** —— 周期与 Key 总额度用量直接归零，新建一把 Key 就从 0 开始。生产上 1615 行账目就是这样没的，而 `requests` 里 55,353,950 tokens 的历史还在。
2. `Prune` 按 `RETENTION_DAYS`（默认 7 天）同时删除 `requests` 与 `key_reservations`。自定义周期最长 60 天、Key 总额度是终身，所以用量会随时间「自己减少」：周期额度实质上退化成一个 7 天滚动窗口。

**改了什么**

- 迁移 **v20**：把 `key_reservations` 重建为**不带外键的独立账本**。`key_id` / `model_id` 变成纯归属标记（0 = 对应对象已删除），`group_id` 与统计口径不变；索引与 `prevent_active_reservation_delete` 触发器原样重建。
- 迁移里按 `requests` 的实扣值**补回旧版本已经丢掉的账目行**（`request_id` 缺失才插入，可重复执行）。生产升级后恢复 1615 行 / 55,353,950 tokens。
- 删除 Key / 模型 / 渠道不再依赖外键级联做保护，改为显式检查：**还有 `reserved` 状态的请求时拒绝删除**（与旧行为一致），结算完成后可删，已结算账目保留。
- `Prune` 只清理 `requests`（含诊断字段的请求明细），**不再裁剪 `key_reservations`**。账本行只存计费数字，不含 prompt / 回复 / 密钥。
- 文档同步：迁移表补 v20，额度章节写明「账本不随保留期裁剪、不随主体删除消失」。

**验证**

`go build` / `go vet` / `go test -count=1 ./...` 全绿，新增两个用例（删 Key 后组用量不变、7 天保留期不裁剪 60 天周期用量）。用**生产库副本**跑真实升级：迁移到 v20、账目补回 1615 行、`pragma integrity_check` ok、外键为空。真实进程端到端 20 项全过，含「用完 429 → 连试 5 次仍 429 → 删 Key → 同组新 Key 仍 429 → 调大限额立即恢复」。

**注意**

周期到期（到达 `period_limit_start + period_limit_days`）后仍按既有语义交给周限额；这一条没有改动。

## v0.7.1 — 周期额度用满后不再「从 0 重新计」，改为硬停

**当时存在的问题**

阶段 B 的 `periodQuotaTransition` 会在周期 Token/金额用满时返回「用满那一刻」，调用方据此把周窗口起点挪到该时刻。结果是：用量显示归零、周限额从交接点重新累计、后续请求继续放行 —— 运维看到的是「额度明明用满了，服务却没有关闭」。这被当作设计写进了交接文档（v0.6.1 的已知行为），但与实际预期相反。

**改了什么**

- `periodQuotaTransition` 改成 `periodWindowUsage`：只统计当前周期窗口内的真实用量，不再计算/返回交接点。
- `ReserveRequest` 在周期生效时直接用 `overdrawn` / `overdrawnAmount` 判定：用满即返回 **429**（`token_quota_exceeded` / `amount_quota_exceeded`，`scope=period` 带数字），不再改 `weekStart`、不再把周窗口起点挪到交接点。沿用「欠费即拒」口径：调大限额后下一次请求立即恢复，不是永久锁死。
- `GroupOverview` 去掉交接逻辑：周期卡片始终显示当前周期的累计用量（用满后不会归零）；`period.transition_utc` 保留字段兼容前端，恒为空串。周期到期后仍按既有语义交给周限额。
- 管理台额度弹窗/卡片文案、README、`docs/admin-api.md`、交接文档同步改为「用满即关闭服务」。
- 测试改写：原来钉住「用满交接周窗口」的 4 个用例改为钉住「用满 429 + 概览用量不归零 + 调大限额恢复 + 其它分组不受影响」；周期到期交接周的用例保持不变。

**验证**

`go build` / `go vet` / `go test -count=1 ./...` 全绿；真实进程端到端（隔离目录）复现：周期限额压到首笔即用满 → 第二笔 429 `scope=period`，管理台周期用量保持真实累计值、不再归零。

**注意**

- 无数据库迁移、无配置变更；回滚只需把 `.env` 版本改回 `v0.7.0`。
- 另一个口径风险（本次未改）：删除客户端 Key 会按外键级联清掉 `key_reservations`，所有窗口用量随之归零（`requests` 历史行保留）。要彻底消除「删 Key 也能重置额度」，需把额度统计改为基于 `requests` 表或改外键为 `ON DELETE SET NULL`，属架构级改动，需另行确认。

## v0.7.0 — 故障转移供应商（单一模型类别 + 自动路由）

**当时存在的问题**

「供应商」是「一个上游渠道 → 一堆模型」的结构：同一个模型名只能绑定一个上游。上游 502/429、密钥失效或模型下架时，客户端会直接拿到错误，只能运维手工改渠道或改客户端配置。想要「同一个模型名后面挂多家供应商、坏一家自动换下一家」，原有数据模型里没有承载它的位置。

**改了什么**

- 迁移 v19：新增 `model_pools`（一个池 = 一个对外模型名）+ `model_pool_members`（成员、优先级、启停）。纯新增两张表，不改任何既有表；升级不影响现有渠道、分组、账目。
- 管理台新增与「供应商」并列的页面，支持创建/编辑/删除、启停、从已有供应商模型里勾选成员、↑↓ 调优先级、临时停用成员；后端 API 为 `/admin/api/pools`（仅管理员可读写）。
- 请求池名时按优先级依次尝试成员：连接失败 / 超时 / 5xx / 429 / 401/403 / 404 / 上游响应无效会切换，400/422 / 客户端取消 / 整体时长超限不切换。失败成员冷却 60 秒（进程内、重启清零、只改优先级不禁用）。
- 授权口径不变：实际候选 = 池成员 ∩ 该 Key 的授权模型；池名只在至少一个成员可用时出现在 `/v1/models` 与「接入信息」。
- 一次请求一次预留/结算；账目 `model_id`/`provider_id` 改为记录实际成功（或最后尝试）的成员，实扣按该成员单价与分组倍率计算。流式只在响应头之前切换。
- 顺带修文档：`README.md` 曾把已实现的 `/v1/responses` 列为「未实现」、changelog 版本范围停留在 v0.3.7、`.env.example` 残留已删除的 `DOCS_ENABLED`；`docs/admin-api.md` 的迁移表补齐到 v19。

**验证**

`go build ./...`、`go vet ./...`、`go test -count=1 ./...` 全绿；新增 3 组测试覆盖存储（迁移/CRUD/顺序/名称冲突/授权裁剪/级联）、转发（主成员 503 → 备用成功、按备用单价计费、账目归属、全失败、冷却、400 不切换、分组越权成员不被调用、流式响应头前切换）、管理端与公共接口（CRUD、管理员限定、`/v1/models` 出现池名）。

**注意**

- 无破坏性配置变更；回滚只需把 `.env` 的 `CIVIC_RELAY_VERSION` 改回 `v0.6.1`（旧版本不读新表，数据保留）。
- 冷却只影响优先级，不是熔断；全部成员都不可用时仍会逐个尝试后返回最后一个错误。
- 池名不得与任何模型 `public_name` 或其它池名重复（双向校验）。

## v0.6.1 — 概览指定不存在的分组改为 404

**当时存在的问题**

`GET /admin/api/overview?group_id=<不存在的组>` 返回 200，并附一个全 0 的 `group` 块。
前端「统计范围」下拉若还指着一个刚被删掉的分组，页面会显示额度全空——看起来像「这组额度
用完了」，实际是这个组已经不在了。根因是 `GroupOverview` 对不存在的组故意返回空概览
（容忍「组刚被删、管理台还在轮询」），这个宽容度是设计，但 handler 不该把它当成正常响应。

**改了什么**

- 管理员显式传 `group_id` 时先 `GetModelGroup` 校验，`sql.ErrNoRows` → **404 `not_found`**。
- 密钥主体路径不加校验：它的 `group_id` 来自密钥绑定，跨组早已 404。
- `TestAdminOverviewGroupSwitch` 增加 `999999 → 404` 断言。

**注意**：无数据库迁移（schema 仍 v18），回滚只需把 `.env` 的 `CIVIC_RELAY_VERSION` 改回 `v0.6.0`。

## v0.6.0 — 控制台必须登录，密钥主体只看自己那组（阶段 C）

**当时存在的问题**

管理台是个「匿名只读」页面：任何人打开 `/admin/` 就能看到全站概览、所有供应商、所有分组、
用量分析。分组与额度分片做完了，这层却还敞着——分片在「谁能看」这件事上等于没做。
老板的原话：「先让用户输密钥，输入了密钥才能看到对应分组信息，而目前是谁都能看到」。
另一件事是角度问题：概览只有全站数字，想看某个组必须绕到模型组页面点「概览」弹窗。

**改了什么**

- **没有任何匿名路径**。`/admin/api/` 一律先认人：管理员用 `X-Admin-Key`，分发出去的客户端密钥
  用 `Authorization: Bearer crk_…`。登录框自动判别两种密钥，`app_…` 应用型标识显式拒绝
  （它的明文创建时即丢弃，无可验证物）。
- **密钥主体是只读且按分组裁剪的**：能看自己那组的概览、额度、渠道（不含上游地址）、授权模型、
  自己的请求明细与「我的用量」；看不到别的组、别的密钥、运行配置、插件，也做不了任何写操作。
  跨组一律 404 而非 403——组 ID 是自增整数，403 等于确认它存在。
- **概览页保留全站数据，另加「统计范围」下拉**：全部分组看全站；选一个组则看到该组四个窗口的
  额度卡片、本组 RPM、进行中、成功率，最近请求也随之切到该组。用量分析的筛选条件里同样加了分组。
- 四种登录拒绝分开返回：`authentication_required` / `invalid_api_key` / `token_expired` /
  `console_login_not_supported`，前端各自出文案——过期该续期，无效该换凭据，别让用户瞎试。
- 新增 `GET /admin/api/me`（自己这把密钥的用量、限额、有效期、可用模型数），概览页的
  「我的用量」直接复用。

**注意**：这是**破坏性变更**。任何脚本若依赖「不带凭据也能读 `/admin/api/overview`」，
升级后都会拿到 401。

## v0.5.0 — 额度从全局搬进每个分组

**当时存在的问题**

全局额度（`relay.env` 里的 `TOKEN_LIMIT_*` / `AMOUNT_LIMIT_*` / `PERIOD_LIMIT_*`）是**整个网关共用一份**。
但分组已经是「一个团队 / 一个软件一条通道」的单位，共用一份额度意味着：A 组把今日用量打满，
B 组的客户端全部 429；想让内部组宽松、外包组收紧，只能靠 Key 级总额度勉强凑，而 Key 额度是
**累计不轮换**的，对「每天 5 元」这种需求完全不对路。分组概览也一直按「走组内渠道的请求」统计，
与额度扣减的口径（按账目行归属）不是一回事，两边数字对不上时无从判断谁对。

**改了什么**

- 迁移 v18：`model_groups` 加 10 列（4 窗口 × Token/金额 + 周期长度 + 周期起点），全部可空，
  `NULL` 或 `0` = 不限。**升级不会让任何分组突然被限额**（不设就是不限）。
- 判定改为在预留事务内**从密钥所属分组那一行**读额度，改完下一次请求即生效；`QuotaLimits`
  保留原字段但语义从「全局配置快照」变成「本次请求生效的额度」，五个窗口判定函数逻辑一行未改。
- 启动播种：`relay.env` 里残留的全局额度会被灌进**每个现有分组**（只填还没设过的列），
  然后从文件里删键；删键本身就是幂等标记。日志 `全局额度配置已灌入 N 个分组并从 relay.env 移除`。
- 管理台：概览摘掉四张全局额度卡（全局视图已经没有限额可展示）；模型组列表加「额度」列
  （三个主窗口最紧张的那个占比，≥80% 黄、用满标红「已欠费」）；组编辑弹窗加 9 个额度输入框
  （`0 = 不限；留空 = 保持原值`，金额按元进出、库里存微元）；组概览弹窗用四张额度卡展示
  「已用 / 本组限额」，口径说明改为「仅计入归属本组的请求」；删组确认写明将解绑多少把密钥。
- 顺手补掉阶段 A 的两处欠账：密钥编辑弹窗里**当前分组即使停用也显示**（标「已停用」），
  且只在选中值真的变化时才 `PUT /group`（避免「只改名字却静默解绑」和停用组的 400）；
  首次启动日志区分「首启」与「恢复既有凭据」两种文案。

**踩过的坑**

| # | 坑 | 后果 / 修法 |
|---|---|---|
| 1 | 周期起点自动填的是**秒级** RFC3339（`…48Z`），账目行是 RFC3339Nano（`…48.219Z`）；SQL 里按**文本**比较，`48Z > 48.219Z` | 同一秒内写入的账目被整段排除在周期窗口外，**周期额度静默失效**（永远 0 用量、永不拒绝）。窗口边界全部改 `julianday()` 数值比较 |
| 2 | 播种时把「没设」写成 `0`、金额用 `ParseInt` 读 | 前者会让所有分组从 NULL 变 `0`（语义上仍是「不限」，但丢掉了「未设」），后者把 `12.5` 截成 `12`。改为 `COALESCE(col, NULLIF(?, 0))` + `ParseFloat × 1e6` |
| 3 | `config.Store.Write` 会把未知键**合并**回文件 | 用它在播种后删键等于没删（下次启动又灌一遍）。新增 `WriteMapping`（不合并）专用于此处 |
| 4 | 前端把 `TensionPct == 0` 一律渲染成「不限」 | `0` 有两种含义：没设限额 / 设了但一点没用。必须看 Token 三列本身，否则刚设完额度的组还显示「不限」，运维以为没生效 |
| 5 | 自定义周期**只填天数不填周期限额**不生效（既有语义，`periodActive` 要求至少一项周期限额） | 界面上原本没说，运维填完 3 天以为已生效。编辑弹窗里写明「要同时填周期长度与至少一项周期限额」 |

**BREAKING CHANGE**：`TOKEN_LIMIT_5H` / `TOKEN_LIMIT_DAILY` / `TOKEN_LIMIT_WEEKLY` /
`TOKEN_LIMIT_PERIOD` / `AMOUNT_LIMIT_5H` / `AMOUNT_LIMIT_DAILY` / `AMOUNT_LIMIT_WEEKLY` /
`AMOUNT_LIMIT_PERIOD` / `PERIOD_LIMIT_DAYS` / `PERIOD_LIMIT_START` 不再从 `relay.env` 读取。
`GET /admin/api/overview` 也不再返回 `five_hour` / `daily` / `weekly` / `period` 四个窗口
（改看 `GET /admin/api/groups/{id}/overview`）。旧部署升级后额度会自动搬进各分组，行为不变。

**已知但尚未实现**

- `_e2e/run_e2e.py` 的 39 项断言里「额度对照实验」依赖已删除的全局额度配置接口，本版本后**必然失效**。
  本机没装 Python 跑不了，也不做盲改——待装好 Python 后改为「按分组设额度 + 断言 429 带分组名」重跑。
- 金额展示仍有历史遗留的 `¥12.500000` 形态（`fmtYuan` 对非整元的 6 位小数尾部零只剥 3 个）。
  属全局金额格式，改动会波及请求日志与用量分析，留待单独处理。

## v0.3.7 — 修复「流式对话突然中断」（线上故障）

**当时存在的问题**

| # | 问题 | 后果 |
|---|---|---|
| 1 | 上游 HTTP 客户端设了 `http.Client.Timeout = connect+read+write`（默认 **340 秒**）。这是**整个请求的总超时，包含读取响应体的全部时间** | 任何超过 340 秒的流式回答被**无声掐断**。记录里只留 `upstream_status=200` + **零 token** 的 `failed`，从管理台完全看不出是超时 |
| 2 | `MAX_STREAM_DURATION`（默认 30 分钟，管理台可配）**从未作用到请求上**，只被后台回收循环当作「陈旧预留」的阈值 | 管理台显示 30 分钟、实际生效 340 秒，两个数字互相矛盾且无人能察觉 |
| 3 | `UPSTREAM_*_TIMEOUT` 改了需要**重启容器**才生效（启动时按值交给 Registry），但 `RestartOnlyChanges` 只列了 `HOST`/`PORT`/`DB_PATH` | 管理台显示「已即时生效」，运维据此以为调大了超时——排查时最容易走错的一步 |

**修复**

- 上游客户端**不设总超时**，职责拆开：「上游不响应」→ `UPSTREAM_READ_TIMEOUT`（`ResponseHeaderTimeout = connect + read`）；「流跑多久」→ `MAX_STREAM_DURATION`（relay 层用 context 施加，**0 = 不限**）；「客户端断开」→ 请求自身 context。

## v0.3.6 — 应用型凭据（客户端里没有密钥）

**当时存在的问题**：客户端**必须持有 `crk_` 密钥**。而写进客户端里的任何秘密迟早会被提取 —— 用户能把密钥带去别的软件里用。

**修复**：`keyless: true` 创建**应用型凭据**，服务端生成公开的应用标识（`app_…`）并**丢弃密钥明文**（不返回、不落盘），客户端只用请求头 `X-App-Id` 接入。两套认证**互不越界**（密钥型的 `public_id` 为空，应用型无法用 Bearer），同给时密钥优先、失败回落应用标识。

> ⚠️ 边界：应用标识是**公开的**，能访问到网关的人都能调用 —— 真正的门是「谁能访问到网关」（内网/防火墙/反代），因此必须配并发与额度上限。跨不可信网络的正确做法是让客户端连**你自己的中转服务**。

**踩过的坑**：创建应用型凭据时先清空 token 再算摘要 → 所有记录得到同一个「空串 HMAC」→ 撞 `token_digest` 的 UNIQUE 约束。必须**先算摘要再丢弃明文**。

## v0.3.5 — 短时令牌（客户端凭据会自己过期）

**当时存在的问题**：客户端 Key **永久有效**，只有手动停用/删除/重置才失效。凭据泄露后除非有人发现并吊销，否则一直可用。

**修复**：`client_keys.expires_at_utc`（`NULL` = 永久，**历史 Key 不受影响**）。创建/编辑可设 `ttl_seconds`（**三态**：缺省 = 不动、`0` = 改永久、`>0` = 从现在起重新计时即续期）。过期返回 **401 `token_expired`**（与 `invalid_api_key` 分开，客户端才知道该换令牌而不是当服务故障重试）。管理台显示剩余寿命（不足 24 小时标黄、过期标红）。

> 「留空不改有效期」这条必须守住，否则「重命名」会变成静默的永久续期 —— 已由 `admin_test.go::TestAdminKeyTTLThreeStates` 钉住。

## v0.3.4 — 客户端接入信息

**当时存在的问题**：明文密钥只在创建/重置时返回一次，Base URL 与模型名又分散在配置页和模型页，运维要自己拼 —— 拼错的表现是客户端 400/404，从错误信息里看不出是「填错了」还是「服务坏了」。

**修复**：`GET /admin/api/keys/{id}/connection` 一次给出 Base URL（按访问管理台的方式推断）、派生地址、脱敏密钥标识、**可用模型清单**（与公共 `/v1/models` 共用同一份 SQL，不会漂移）、所属分组、`issues`/`warnings`/`ready`。管理台 Key 行有「接入信息」按钮。

## 已知但尚未实现

- **客户端指定分组**：现在分组由服务端按凭据绑定决定，客户端不能选。要做需加「请求头指定分组 + 校验在该凭据已绑定的范围内」。
- **客户端自助换令牌**：短时令牌到期需管理员续期。若要客户端自己换，需要一层「用旧令牌换新令牌」的接口，并限定「仅临近过期时可换一次」。
- **公共接口的 CORS**：当前不带 `Access-Control-*` 头（`OPTIONS` 返回 405），网页类客户端**不能跨源直连**，必须走同源反向代理。要支持需显式加 CORS，但那会让 relay 对任意网页开放（浏览器里密钥明文可见），只在完全可信环境才建议。
