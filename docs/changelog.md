## v0.13.2 — 客户端密钥登录后只保留三个页面

**背景**

客户端密钥是发给使用方的（外包、同事、别人机器上的程序）。他们登录管理台是为了自查
用量、看请求为什么失败，不是来运维网关的。此前导航里仍摆着「供应商」「成员组」，点进去
是裁剪过的只读视图（无上游地址、无成员组名），但两个页面的存在本身就在暗示「这里由我
管」；渠道名还从概览与请求日志的「渠道」列成列出现——隐藏入口却没隐藏信息。

**改了什么**

- **导航按主体裁剪**：`providers` / `groups` 两个入口挂上 `.admin-only`（只读主体下由
  CSS 直接不渲染），视图容器也打上同一标记，切换逻辑再按导航标记挡一道——即使从控制台
  调 `showView("providers")`，也会回落到运行概览而不是把页面渲染出来。
- **概览与请求日志去掉「渠道」列**，请求日志筛选里的「渠道 ID」一并隐藏；只读主体不再
  拉 `/admin/api/providers`（少一次全量请求，也少一份能被翻出来的渠道名）。
- 概览 / 用量分析不再为只读主体拉全量分组列表——分组筛选本来就对它们隐藏，这份数据只是
  白拿。
- 顺手修掉概览首屏模型名显示成「#1」：名称缓存原来是 fire-and-forget，渲染时经常还没
  回来，现在先 `await` 再渲染。

**边界**

后端权限没变：客户端密钥仍可调用 `/admin/api/providers`（只返回自己分组能用的渠道，且
不含上游地址）。本次只改界面可见性，**不要把隐藏当权限**——真正的隔离仍是服务端按分组
裁剪与跨组 404。

## v0.13.1 — 收紧三道并发闸的一致性（Key 并发）

**背景**

v0.13.0 给成员组加了并发上限之后复查了一遍并发链路。现在同时有三道闸：
全局 `GLOBAL_CONCURRENCY_LIMIT`（relay 层）、Key 自己的 `concurrency_limit`（relay 内存
计数器 + 账本事务内兜底）、分组 `concurrency_limit`（账本事务内）。分组那道是新加的，
检查时发现 Key 这道有两处与它不一致，会让运维误判。

**改了什么**

- **Key 并发上限改完立刻生效**：内存计数器（`KeyGates`）原来只在某个 Key 的 gate 首次
  创建时采用传进来的 limit，之后一直用旧值——把上限从 1 调到 5，仍会被旧值挡着；从 5
  调到 1，又能多放几个进来，直到这把 Key 的请求全部结束、gate 被回收才轮到新值。现在
  每次取名额都会把当前上限同步进 gate：调大立即放行，调小只拦新请求、不动在跑的。
- **Key 并发 429 能看懂是谁挡的**：原来全局并发与 Key 并发共用 `rate_limit_exceeded`，
  `message` 还是默认的 `request could not be completed`，客户端与运维都分不清是网关满了
  还是这把 Key 满了。现在 Key 这一路会带上 Key 名与数字（「Key「外包A」并发已满（在跑 1，
  上限 1），请等前面的请求结束后重试」），全局那一路单独给「网关并发已满」。
  **公共错误码仍是 `rate_limit_exceeded`**，按码做退避的客户端不受影响。
- **密钥列表显示「在跑 / 上限」**：与成员组列表同口径（`status='reserved'` 的行数），
  满额标红、≥80% 变黄，并新增 `ActiveConcurrency` 字段。以前只显示上限数字，看到
  「1」不知道现在是 0/1 还是 1/1，排查 Key 并发只能靠猜。
- **账本层的 Key 并发拒绝补上数字**：`QuotaError{code: concurrency_exceeded}` 现在带
  `Used`/`Limit`，这是上面文案的数据来源；口径不变（事务内 count + insert，跨进程也不超发）。
- 文档把三道闸的职责与计数口径写在一处，并修正了「Key 达到总额度会自动停用」这句早已
  废弃的旧描述（现行为是「用满即拒」，不再自动停用）。

**未改动（明确保留）**

- 分组并发与全局并发仍**各判各的**，管理台不做「必须小于全局」的联动校验。
- Key 的并发上限仍最小为 1（没有「不限」），与分组不同——这是既有约定。

**验证**

- `gofmt -l` / `go vet ./...` / `go test ./... -count=1` 全绿。
- 新增用例：Key 上限调大/调小在请求在跑时立即生效（内存闸）；账本拒绝带 `1/1` 数字；
  公共接口 429 文案含 Key 名与「在跑 / 上限」且错误码不变；密钥列表返回 `ActiveConcurrency`。

## v0.13.0 — 成员组可设并发上限

**需求**

成员组是「渠道 + 额度」的池子，额度只能管一段时间里用掉多少，管不了同一时刻有几笔在跑。
上游账号常见的限制恰恰是并发数（超了排队、或者直接 429），瞬时打满时窗口额度还宽裕，
请求就已经开始失败了。老板要求给成员组加一个并发上限，并且明确：**这个上限与全局上限
无关**——全局超了这里当然也算超限，两者各判各的，不需要互相换算。

**设计要点**

- **上限落在 `model_groups` 上**（`concurrency_limit`，`NULL`/0 = 不限），因为「谁在提供这条
  渠道」已经有现成的归属组（v24），成员组与聚合组共用一套判定，不需要给成员组另建表。
- **按 `source_group_id` 计数**：与额度扣减同口径。成员组的渠道被聚合组调用时才占成员组的
  名额；聚合组自有渠道的请求计入聚合组自己。这样「一个渠道只属于一个组」这条不变量在
  并发这一层同样成立。
- **判定放在预留事务里**：`ReserveRequest` 全程持有 `reservationMu` 且用 `BEGIN IMMEDIATE`，
  「先数后插」不会超发；不需要另建内存计数器，也不需要处理它与重启/多实例的一致性问题。
- **与全局并发上限解耦**：全局那道闸在 relay 层（进程内 limiter），组这道闸在账本层，任一
  超了都返回 429。管理台不做「不能大于全局」的联动校验——那是两种不同口径的数字。
- **错误文案不套额度那套话术**：并发满不是「欠费」，不需要等窗口轮换，前面的请求一结束
  就恢复。文案直接写「并发已满（在跑 N，上限 M），请等前面的请求结束后重试」，否则运维
  会被引去调额度。

**改了什么**

- 迁移 **v26**：`model_groups` 加 `concurrency_limit`（默认 `NULL`）；建
  `key_reservations(source_group_id,status)` 索引供计数。纯新增，既有组不限并发。
- 组模型与 CRUD 接通新列；`0` 归一成 `NULL`（不留「0 = 不限」的第二种表示）。
- `checkGroupConcurrency` 在预留事务内判定，超限返回 `QuotaError{code:
  group_concurrency_exceeded}`；`Detail()` 单独出并发文案。公共接口沿用既有的
  `errors.As` 分支，自动映射成 429。
- 组列表返回 `ConcurrencyLimit` / `ActiveConcurrency`（实时在跑数），管理台显示「3 / 5」，
  名额满时标红「已满」。
- 管理台：创建表单与编辑弹窗都能填并发上限（留空 = 保持原值 / 不限，0 = 不限），
  编辑弹窗提示当前在跑几个；只读视图也能看到。

**验证**

- `go vet` + `go test ./... -count=1` 全绿。新增 store 用例覆盖：名额占满被拒（含错误码、
  归属组、数字、文案）、结算后名额释放、按组独立计数（A 组占满不影响 B 组）、默认不限、
  填 0 归一成 NULL、改名不清上限、负数拒绝、列表带实时占用；接口层覆盖创建/列表/改名/
  清空/负数 400，以及公共接口的 429 + 中文文案。

## v0.12.0 — 生效时段支持多段，每段可单独设星期

**需求**

「每天重复」原来只能配一对起止分钟 + 一组星期。实际排班不是这样：工作日只在夜里
跑、周末全天跑；或者白天午休两小时。前者用一组全局星期表达不了，只能拆成两条渠道
——而 v24 刚把「一个渠道只能属于一个组」定成规则，拆开就意味着要两个上游账号。

老板的要求：这个弹窗要能加多段，并且**星期几要能按段单独设**。

**设计要点**

- **星期从「渠道级」下沉到「段级」**：`ScheduleWindow` 带自己的 `Weekdays` 掩码。
  渠道级的 `schedule_weekdays` 仍然保留，但只服务于「单段老写法」——这样 v25 之前
  的数据不需要回填，读取时 `schedule_windows` 为空就回落到旧列。
- **一段都不选 ≠ 每天（在界面层）**：后端把空星期当成「每天」（与顶层字段一致），
  但管理台会拦住「一段的所有星期都被取消」——那一段永远不生效，几乎总是误操作，
  而「全天」有专门的表达（起止相同）。
- **回滚安全**：写入时把第一段（含它的星期）同步回单段列。旧版本读不到多段，至少
  还保留一段有效时段，不会整条渠道退化成「全天可用」。
- **判定仍然是唯一一处**：`ProviderSchedule.ActiveAt` 逐段扫，跨零点按「段开始那天」
  算星期；授权、路由、故障转移、探活、模型同步全部走这一个函数，不存在第二套口径。
- **上限与去重**：最多 24 段（一天 24 小时上限够用，拦住脚本误写上千段）；起止 + 星期
  完全相同视为重复段，保存时合并，按开始时间排序。

**改了什么**

- 迁移 **v25**：`providers` 加 `schedule_windows TEXT NOT NULL DEFAULT ''`（JSON 数组）。
- `ScheduleWindow` 新增 `Weekdays`；`ActiveAt` 由「一个全局星期」改成「逐段判定」；
  单段回落时用旧列构造一段。`decodeScheduleWindows` 把 0 与越界掩码归一到「每天」，
  坏 JSON 返回空——让判定回落到旧列，而不是把渠道永久判成不在时段。
- `ProviderScheduleInput` / `ScheduleWindowInput` 支持 `Windows`（钟点 `HH:MM` +
  每段 `weekdays`）；`NormalizeProviderSchedule` 逐段校验，错误文案带「第 N 段」。
- `providers` 的读写列同步（`providerSelect`、创建、更新、`UpdateProvider` 回读），
  以及三处「按 id 取时段」的查询：可用模型过滤（`filterByProviderSchedule`）、
  分组探活（`GroupMonitorTargets`）。
- 管理台：时段弹窗改成「段列表」——每段一行 = 起止时间 + 7 个紧凑星期格 + 删除；
  「+ 添加时段」；只剩一段时删除按钮置灰；供应商列表的「启用时段」列按段展示
  （`全天 周六至周日，22:00-08:00 周一至周五 · 跨零点`）。

**验证**

- `go vet` + `go test ./... -count=1` 全绿。新增用例覆盖：多段命中/空档、跨零点段与
  普通段混排、每段独立星期（工作日夜间 + 周末全天）、单段回落、排序与去重、
  段数上限、空数组拒绝、编解码容错、落库回读、改名不清时段，以及接口层的提交/回读。
- 本地实例（v24 库升到 v25）：给一条渠道配「周末全天 + 工作日 22:00-08:00」，PUT 与
  GET 都返回两段各自的掩码（`0b1100000` / `0b11111`），单段列回写第一段。
- Chromium 实开时段弹窗：两段星期分别高亮、加段默认全选、布局不溢出；供应商列表
  的时段列单行显示完整信息，操作列没有被挤出可视区。

## v0.11.1 — v0.11.0 的审查修复

**背景**

按惯例把 v0.11.0 的改动再审一遍。这次找出来的问题都集中在「v24 的新规则没有铺到每
一条既有路径上」：数据模型改了，但错误出口、返回对象、SQL 口径、只读视图还有按旧
世界写的分支。

**修了什么**

- **改不存在的组，报的是 SQLite 原文**：`GET/PUT /admin/api/groups/{id}/providers`
  直接落到 `SELECT ... FROM model_groups`，组缺失时把 `sql: no rows in result set`
  包成 `400 group_invalid` 抛给运维。与 v0.10.1 修过的「Key 绑不存在的组」是同一类
  问题，这条路径当时漏了。现在两条方法都先判组存在，缺失一律 404 `not_found`；
  「分组已停用」也从英文 `model group is disabled` 改成中文。
- **改渠道的响应里归属是空的**：`PUT /admin/api/providers/{id}` 末尾就地拼 `Provider`
  字面量，v24 新加的 `GroupID/GroupName` 没填。管理台保存后会重拉列表所以看不出来，
  直接用 API 的调用方会以为「改个名字把渠道改出分组了」。改为写完后回查一次。
- **只读视图给每条渠道挂假黄标**：密钥主体的 `GET /admin/api/providers` 已被后端抹空
  归属字段，前端却照着渲染，于是登录成客户端密钥后每条渠道下面都标「未加入分组」。
  这个标签的用途是提示管理员「这条渠道的模型不会被授权」，出现在只读视图里纯属误导。
- **记账的 `source_group` 还留着多组时代的消歧**：`MIN(child_group_id)` 在 v24 之后
  永远只有一行，留着会让后来者以为归属仍有歧义。改成直接读渠道的归属组，并确认它是
  本组或本组的启用成员组；顺带去掉了每次预留都要跑的聚合子查询。
- **四份 SQL 的成员分支没钉 `kind`**：授权（`authorizedModelsSelect`）、倍率
  （`KeyModelRateMilli`）、监测（`GroupMonitorTargets`）、组作用域渠道
  （`EffectiveProviderIDs`）都只校验了成员组 `enabled`，没校验它是 `normal`。写入时
  有校验，但历史数据（`kind` 是 v23 才有的概念）和手工 SQL 不受约束——「聚合组包含
  聚合组」一旦出现就是授权范围的静默放大。四份口径同时补上 `cg.kind='normal'`。
- **并发保存报英文**：两个运维同时改分组时，WAL 下先读后写的事务可能拿到
  `database is locked`（不是唯一约束），原来的翻译只认 `unique constraint`，于是这
  条路径把 SQLite 原文丢给用户。补上 BUSY 识别，统一成「保存冲突，请稍后重试」。

**验证**

- `go vet` + `go test ./... -count=1` 全绿。
- 新增 4 个用例：不存在的组 GET/PUT 都 404 且不含 SQL 原文；`PUT /providers/{id}` 的
  响应仍带归属组；聚合组**自有渠道**的 `source_group_id` 记在聚合组自己头上（改写后
  的第一条分支）；不存在的组保存渠道直接报错。

## v0.11.0 — 一个渠道只能属于一个组

**需求**

v0.10.0 之后还剩一个说不清的角落：同一条渠道可以同时挂进两个成员组，而一笔请求的
账目只能记到一个组上，于是必须替它挑一个「真正提供者」（取 ID 最小的成员组）。结果
是最小 ID 的组承担全部用量、另一个组永远显示 0，而它明明在提供渠道；更糟的是只有
最小 ID 组的额度用满才拒请求，哪怕另一个组还有大把余额——「分池限流」这个最常见的
用法正好失效。

老板给的解法比「挑一个」彻底：**一个供应商只能被包含进一个组**。

**设计要点**

- **归属唯一，计费就不用猜**：账本里 `source_group_id` 从此恒等于「这条渠道的归属组」，
  不需要 `MIN()`，也不存在「用量记在 A、渠道其实是 B 的」。同一家上游要开两个账号
  分别限流，就是两条渠道——现实里它们本来就是两个凭据，账单也确实是两笔。
- **应用层 + 数据库两层**：`ReplaceGroupProviders` 在事务里校验并返回可读冲突；迁移
  同时建 `UNIQUE INDEX group_providers(provider_id)`。脚本、手工 SQL、并发窗口都绕不过
  唯一索引，应用层负责把冲突翻译成人话。
- **同组重复保存仍幂等**：替换写是先删后插，校验只排除 groupID 自己，否则「改个组名
  顺手保存渠道」会把自己挡下来。
- **迁移只收敛数据，不改计费语义**：重复关系里被保留的是**最早建立**的那条（rowid
  最小），因为过去从未被计费的是其余几条（用量恒为 0），删掉不动任何历史数字。
- **界面上不让人撞墙**：已经在别组的渠道直接置灰并写清在哪个组，而不是等保存后弹错。

**改了什么**

- `ReplaceGroupProviders` 事务内校验归属，新增哨兵 `ErrProviderGrouped` 与
  `*ProviderGroupConflict`（带渠道名、组名）；`POST /admin/api/groups` 与
  `PUT /admin/api/groups/{id}/providers` 返回 400 `provider_in_use`（不再笼统
  `group_invalid`），建组失败时**不会留下这个组**。
- 迁移 **v24**：去重（保留最早建立的归属）+ 唯一索引（替换原来的普通索引）。
- `Provider` 新增 `GroupID`/`GroupName`（由 `ListProviders`/`GetProvider` 填充），
  `GET /admin/api/providers` 带出归属；组作用域主体（非管理员）这两个字段留空，
  不泄露成员组命名。
- 管理台：供应商列表在名称下方显示归属组，未入组显示黄色「未加入分组」（这类渠道
  的模型不会被任何 Key 授权，是最常见的「配好了却调不通」）；成员组/聚合组的创建与
  编辑勾选列表里，已在别组的渠道置灰 + 标注「已属于「X」」；进入这两个页面与打开
  编辑弹窗时强制刷新渠道归属，避免用过期缓存显示出「可选」。
- 既有测试里「同一渠道挂两个组」的用例按新规则改成「每组各一条渠道」（同一上游的
  两个账号）；`TestAggregateGroupPrefersOwnProvider` 的前提已不可能成立，改为
  `TestAggregateCannotAlsoOwnMemberProvider`。

**验证**

- `go vet` + `go test ./... -count=1` 全绿；新增 3 个存储用例（重复归属被拒且不留
  半成品 + 唯一索引兜底、`ListProviders` 带出并清空归属、v24 去重只动重复项）与
  2 个接口用例（建组即带 / 单独改渠道两条路径都 400 `provider_in_use` 且列表里不多

## v0.10.1 — 审查 v0.10.0 的边角：孤儿 Key、渠道可见性、成员组倍率

**为什么改**

v0.10.0 把「只有聚合组能对外」落到了写、读、记账三条路径上，但周边还有几处是按
旧语义写的。逐个查过一遍后修掉下面这些——都不影响主流程，但都会在某个具体操作上
给出错的结果或错的解释。

**改了什么**

- **建 Key 绑组失败会留下孤儿 Key**（真 bug）：`CreateClientKey` 先落库、再 `SetKeyGroup`，

  （校验与绑定之间组刚被停用/删除）就把刚建的 Key 删掉，保证「报错 = 什么都没发生」。
- **绑不存在的组会把 SQL 原文抛给运维**：`sql.ErrNoRows` 的文本（`sql: no rows in result set`）

- **组作用域的管理视图看不到成员组渠道**：`GET /admin/api/providers` 对「只能管自己组」的

  却没这个渠道。新增 `EffectiveProviderIDs`（自有 ∪ 启用成员组，与授权口径一致）供该视图
  使用；编辑页仍用 `GroupProviderIDs`（只列自有渠道），否则保存会把成员关系复制成自有渠道。
- **接入信息对「绑在成员组」说不清原因**：以前只提示「没有可用模型，检查定价」，现在单独
  一条：所属分组是成员组、请改绑聚合模型组。分组对象也带上 `kind`。
- **成员组倍率是个死配置**：扣费只按「绑定该组的聚合组」倍率算，成员组自己的倍率不参与
  任何计算。原界面让运维改它、并在计价明细里写「倍率后实际扣费 = 单价 × 成员组倍率」，
  给出的是一个永远不会发生的数字。现在成员组页只展示、不可改，计价明细改为「按聚合组
  倍率」。
- 顺手把两处面向运维的旧术语（「普通模型组」）改成「成员组」。

**验证**

- `go vet` + `go test ./...` 全绿；新增接口用例（创建即绑成员组返回 400 且**列表里不多出
  这把 Key**、绑不存在的组给出可读文案）与存储用例（`EffectiveProviderIDs` 覆盖成员组
  渠道、成员组停用后同步消失）。

## v0.10.0 — 只有聚合模型组对外，成员组退回「额度池」

**需求**

v0.9.0 让两种组都能被 Key 绑定，用起来反而更难解释：升级上来的每个组都叫「模型组」、都能绑 Key，而聚合组既能绑又包含别的组，「这笔请求到底扣谁的额度」每次都要重新讲一遍。老板要求：**只有聚合模型组能最终调用，成员组只是「有自己额度的供应商」**。

**设计要点**

- **一个类型只有一种用途**：`aggregate` = 对外（唯一可被 Key 绑定），`normal` = 成员组（渠道 + 独立额度，不对外）。「能不能被调用」从此看组类型，不再看有没有绑 Key。
- **规则落在三条路径上**：写路径（`SetKeyGroup` 拒绝成员组）、读路径（`authorizedModelsSelect` 带 `kind='aggregate'`）、记账路径（`ReserveRequest` 在写账目前拒绝）。只写进文档或只拦一个入口，都会在某个角落漏出去。
- **创建时不传 `kind` 按 `aggregate`**：误建成员组的代价更大 —— 渠道、额度、倍率都能配，却永远接不到请求，排查时很难看出只是组类型选错；误建空聚合组在列表里一眼就能看到「未包含任何组、0 个渠道」。
- **聚合组允许只挂自有渠道**：这样「一个组 + 几个渠道」不必为了凑成员组而多建一层，也不会出现「成员组与自有渠道都空」的死组（界面在创建与编辑时都要求「成员组或自有渠道至少一个」；管理接口不强制，便于脚本先建组再加渠道）。
- **迁移 v23 把没有被任何聚合组包含的 `normal` 组改成 `aggregate`**：它们历史上就是独立对外的组，不转的话升级后既有 Key 会同时失效 —— 这种「升级完全站不通」的故障代价远高于「个别预留中的成员组被当成独立组」。已经是成员的 `normal` 组保留身份；这种组若历史上还绑着 Key，升级后会调不动，Key 列表与编辑弹窗会明确标出来要求改绑。

**改了什么**

- 迁移 **v23**：纯数据语义，无结构变更（`kind` 列 v22 已有）。
- `SetKeyGroup` 校验目标组必须是聚合组，新增哨兵错误 `ErrGroupNotCallable`；`POST /admin/api/keys`、`PUT /admin/api/keys/{id}/group` 返回 400 `group_not_callable` 并带原因（不再笼统 `key_invalid`）。
- `authorizedModelsSelect` 增加 `g.kind='aggregate'`；`ReserveRequest` 在读模型前拒绝成员组上的 Key（纵深防御，正常流程到不了这里）。
- `KeyModelRateMilli` 改为按新口径认成员组渠道：原来只认自有渠道，从成员组来的模型会掉回默认倍率，与预留事务里的报价（永远取绑定组倍率）不一致。
- `GET /admin/api/groups` 增加 `ParentCount`（被几个聚合组包含）。
- 管理台：「模型组」改名「成员组」并排到聚合组之后；两页各加一条页面级说明（谁能被调用）；成员组列表新增「被聚合组包含」列，未被包含的组显著标出；Key 创建/编辑的分组单选只列聚合组；编辑「历史脏绑定」的 Key 时给出黄色警告；删除成员组时把「被 X 个聚合组包含」写进确认框；聚合组创建/编辑允许不带成员组（要求成员组或自有渠道至少一个）。
- 顺手修掉 `TestReapStaleReservationsReleasesQuotaAndConcurrency` 的时序抖动（第二次回收前先结算刚建的预留，否则机器一忙就会把它当成陈旧预留回收）。

**验证**

- `go vet` + `go test ./...` 全绿；新增 4 个存储层用例（成员组拒绝绑定且不留半成品、历史脏绑定也让授权与记账两条出口都拒绝、聚合倍率作用于成员组模型、v23 迁移只提升独立组）与 1 个接口用例（400 `group_not_callable`，创建即绑同样拦）。
- 本地隔离实例用真实 v22 库升级：`schema_migrations=23`，成员组仍为 `normal`（`ParentCount=2`）、两个聚合组成员关系不变；`PUT /admin/api/keys/1/group` 指向成员组返回 **400 `group_not_callable`**、指向聚合组 200，接入信息能列出成员组模型。

## v0.9.0 — 聚合模型组：一个组可以包含其他组

**需求**

渠道和模型已经按「模型组」打包授权，但组之间不能复用：想给一组人同时开放「福利组 + 夜间组」的全部模型，只能把渠道手工复制一遍，之后两边各自维护、必然漂移。老板要求「模型组可以包含其他模型组」，并明确 **两边都扣额度**；为避免和普通组混淆，界面上单开一页「聚合模型组」。

**设计要点**

- **聚合组仍是一行 `model_groups`**（`kind='aggregate'`），不是新表。倍率、九项额度、Key 绑定、概览、账目归属全部按 `model_groups.id` 走，另建表等于把这些逻辑复制一份，两份实现早晚漂移。「聚合组拥有单独的计费」因此天然成立。
- **只允许一层**：聚合组只能包含 `normal` 组，写入时校验、包含自己直接拒绝。不做多层是刻意的取舍 —— 多层要递归解析与环检测，额度归属会变得没人能解释。
- **聚合组也可以直接挂渠道**，等价于「自有渠道 + 成员组渠道」的并集。
- **一笔请求只写一行账本**，但记录两个归属：`group_id`（Key 绑定的组）与 `source_group_id`（真正提供该模型的成员组；普通组两者相同）。双写两行会让所有 `SUM` 翻倍、结算要改多行，是计费系统最容易埋雷的地方。
- **两个组都扣**：额度判定对 `group_id` 与 `source_group_id` 各跑一遍，任一组任一窗口用满就 429，错误里写明是哪个组咬住的。成员组的用量视图按 `(group_id=? OR source_group_id=?)` 统计，与判定同口径 —— 否则会出现「成员组看起来没用量、额度却莫名用满」。
- **计价用 Key 绑定组的倍率**：同一笔请求在两边记同一个金额，这就是「金额同步」的实现；成员组自己的倍率只对它自己的 Key 生效。
- 同一模型被多个成员组包含时，来源组取 **id 最小的成员组**（确定性优先），文档写明。

**改了什么**

- 迁移 **v22**：`model_groups.kind`（默认 `normal`）、`group_compositions(parent,child)`、`requests.source_group_id`、`key_reservations.source_group_id` 及两个索引。纯新增，升级后既有组行为不变。
- 授权口径（`authorizedModelsSelect`）把「组内渠道」换成「自有渠道 ∪ 启用成员组的渠道」；`ReserveRequest` 的模型校验同步改。
- 分组探活与列表、分组概览、分组用量桶、`UsableModelsForKey` 全部按新口径取数。
- 管理端：`POST /admin/api/groups` 支持 `kind` / `group_ids`；新增 `GET|PUT /admin/api/groups/{id}/members`；`GET /admin/api/groups` 返回 `Kind` / `Members` / `Providers`；删组响应带上「被哪些聚合组包含」。
- 管理台新增「聚合模型组」页（列表、创建、编辑、概览、检测、删除）。密钥主体登录时不下发成员组的名字与倍率。

**验证**

- `go vet` + `go test ./...` 全绿，新增 7 个存储层用例（迁移默认值、成员授权、拒绝嵌套/自身、成员额度咬住、成员组用量同步、自有渠道优先、停用成员不授权）与 2 个接口用例。
- 本地隔离实例端到端 **20 项全 PASS**（假上游计费）：`/v1/models` 能看到成员组模型、200 调用成功后两边当日 token 都是 150、金额一致、成员组额度压到 1 后 429 且错误指向成员组、失败创建不留半成品、删聚合组不动成员组。
- Chromium 实开管理台：列表 9 列完整、成员组标签/渠道数正确、编辑弹窗成员已勾选且 9 个额度框齐全、取消可关闭、创建后列表 +1、**0 条 console 错误**。

## v0.8.1 — 生效时段的审查修复

**当时存在的问题**（v0.8.0 上线后复查发现）

1. **「一周都不选」会被静默改成「每天」**：管理台的星期勾选允许全部取消，提交空数组；后端为兼容 API 直接把空数组当 `127`。运维的本意是「哪天都不用」，结果变成每周 7 天全开 —— 按量计费的渠道会一直烧钱。
2. **带秒的时间会让保存直接抛异常**：`datetime-local` 正常只给到分钟，但一旦值带秒，前端拼出 `20:00:00:00+08:00`，`toISOString()` 抛 `Invalid time value`，用户只看到一句英文报错。
3. **全组渠道都在时段外时，探活报 `ok`（绿灯）**：客户端此刻一个模型都拿不到，监控却是绿的，运维只能靠明细里那句话发现。
4. 次要：`PUT` 文档没列出时段字段名（按 POST 的 snake_case 发会静默不生效）；供应商页的「未到时段」标签是快照，页面开着到点不会自己变；`filterByProviderSchedule` 每个请求全表扫 `providers`；转发口径没自带 `k.enabled=1`。

**改了什么**

- 管理台保存 `daily` 时段前校验「至少选一天」，否则提示改选「不限」；后端仍把空数组当每天（API 兼容），语义由调用方负责。
- `bjInputToISO` 按长度区分是否已带秒，无法解析时给出中文错误，不再抛 `Invalid time value`。
- 新增分组状态 **`schedule_idle`**（全部启用渠道都在时段外）：灰色显示、`report()` 静默不打 warn、前端标签「全部渠道在时段外」。同时把「渠道下没有已定价模型」的判断改成只看**时段内**的渠道 —— 原来会因时段外渠道有定价而误判为可服务。
- 供应商页每分钟静默刷新一次（仅在该页、标签可见、未开弹窗时），「未到时段」标签到点自动切换。
- `filterByProviderSchedule` 改为 `WHERE id IN (…)`，只读本次用到的渠道。
- `UsableModelsForKey` 的授权 SQL 自带 `k.enabled=1`（纵深防御，调用方本来已鉴权）。
- 文档：`PUT` 的完整 PascalCase 字段清单、`schedule_idle` 状态语义、`range` 脏数据 fail-open 约定、在途请求不会被到点掐断。

**验证**

`go vet` + `go test -count=1 ./...` 全绿；本地隔离实例用 Chromium 实开管理台，确认星期全不选被拦、带秒时间可保存、`schedule_idle` 状态显示正常（灰色「全部渠道在时段外」）。

## v0.8.0 — 供应商可以只在选定时间段启用

**需求**

有些渠道是「夜间便宜」「只在某个活动期可用」或「按天临时采购」的，以前只能手动开关：到点要人去点，忘了就会出现「白天的请求打到夜间才通的渠道」或「活动结束还在给付费用」。

**改了什么**

- 迁移 **v21**：`providers` 加 6 列（`schedule_mode` / `schedule_start_utc` / `schedule_end_utc` / `schedule_start_minute` / `schedule_end_minute` / `schedule_weekdays`），默认 `always`。纯新增列，**升级后所有既有渠道行为完全不变**。
- 三种互斥方式，由 `store.ProviderSchedule.ActiveAt` 单点判定：
  - `always` 不限（默认）；
  - `range` 固定日期区间，起点含、终点不含，两侧都可留空表示该侧不限 —— 适合「11-13 20:00 到 11-14 08:00 临时开通」；
  - `daily` 每天重复时段，支持**跨零点**（22:00-08:00）与**星期选择**（周一…周日）。跨零点时凌晨那一段归属「时段开始那天」，所以「周一 22:00-08:00」包含周二凌晨。
- 时区固定**北京时间**：`range` 入库归一化成 UTC RFC3339，`daily` 的分钟数与星期按 +08:00 解释；管理台的 `datetime-local` 也按北京时间来回换算，两边不会错开一小时。
- 时段判定接入全链路，只有一处口径（`ActiveAt`）：
  - `/v1/models` 与 `Begin`（真实转发）走 `UsableModelsForKey` —— 时段外渠道的模型对客户端不可见、不可路由；
  - 故障转移池的候选与「池名是否出现在 /v1/models」同口径：池内成员全在时段外时，池名也不出现；
  - 管理台「接入信息」仍走 `AuthorizedModelsForKey`，**不按时段过滤** —— 那是「配置上授权了哪些模型」，运维要能分清「没授权」和「到点才可用」；
  - 分组探活、定时模型同步跳过时段外渠道，避免整夜误报「全部渠道不可达」。
- 管理台：供应商表新增「启用时段」列与「未到时段」状态标签（与「停用」分开显示，免得运维以为配置被人关了）；新增「设置时段」弹窗，含模式下拉、区间输入、每日时段与星期勾选。
- 接口：`POST /admin/api/providers` 用 snake_case（`schedule_mode`、`schedule_start`、`schedule_end`、`schedule_daily_start`、`schedule_daily_end`、`schedule_weekdays`）；`PUT` 沿用本接口既有的 **PascalCase** 契约（`ScheduleMode` 等）。`PUT` 里 `ScheduleMode` 缺省 = 保持原时段，避免「只改名字」把时段顺手清掉。
- 非法输入一律 400 且带可照做的原因（如「结束时间必须晚于开始时间（当前：2026-11-14 08:00 → 2026-11-13 20:00）」），被拒的更新不落库。

**取值约定**

- `schedule_weekdays` 是位掩码：bit0=周一 … bit6=周日，`0` 或 `127` 都表示每天。
- `daily` 起止相同 = 全天（只受星期约束）。
- `range` 脏数据（解析不出时间）按「该侧不限」处理，宁可放行也不让一条脏记录把渠道永久停掉。

**验证**

`go build` / `go vet` / `go test -count=1 ./...` 全绿。新增用例覆盖：`ActiveAt` 的 22 个边界（含跨零点、星期归属、起止相同）、输入归一化与错误文案、CRUD 里「只改名字不清时段」「非法更新不落库」、`UsableModelsForKey` 时段前后切换、`v21` 迁移后旧渠道必为 `always`、管理端 POST/PUT 的字段往返。

**当时存在的问题**

## v0.7.2 — 额度账本独立于主数据，删 Key / 模型不再把用量清零

**当时存在的问题**

v0.7.1 修掉了「周期用满后交接到周窗口」那一条归零路径，但还有两条会让人看到「周期额度从 0 重新计」：

1. `key_reservations.key_id` / `model_id` 带 `ON DELETE CASCADE`。额度是按 `group_id` 统计的，所以**删一把 Key（或删模型、删渠道）会把该组这一段的账目整段删掉** —— 周期与 Key 总额度用量直接归零，新建一把 Key 就从 0 开始。生产上 1615 行账目就是这样没的，而 `requests` 里 55,353,950 tokens 的历史还在。
2. `Prune` 按 `RETENTION_DAYS`（默认 7 天）同时删除 `requests` 与 `key_reservations`。自定义周期最长 60 天、Key 总额度是终身，所以用量会随时间「自己减少」：周期额度实质上退化成一个 7 天滚动窗口。

**改了什么**

- 迁移 **v20**：把 `key_reservations` 重建为**不带外键的独立账本**。`key_id` / `model_id` 变成纯归属标记（0 = 对应对象已删除），`group_id` 与统计口径不变；索引与 `prevent_active_reservation_delete` 触发器原样重建。
- 迁移里按 `requests` 的实扣值**补回旧版本已经丢掉的账目行**（`request_id` 缺失才插入，可重复执行）。生产升级后恢复 1615 行 / 55,353,950 tokens。
- 删除 Key / 模型 / 渠道不再依赖外键级联做保护，改为显式检查：**还有 `reserved` 状态的请求时拒绝删除**（与旧行为一致），结算完成后可删，已结算账目保留。
- `Prune` 只清理 `requests`（含诊断字段的请求明细），**不再裁剪 `key_reservations`**。账本行只存计费数字，不含 prompt / 回复 / 密钥。
- 文档同步：迁移表补 v20，额度章节写明「账本不随保留期裁剪、不随主体删除消失」。

**验证**

`go build` / `go vet` / `go test -count=1 ./...` 全绿，新增两个用例（删 Key 后组用量不变、7 天保留期不裁剪 60 天周期用量）。用**生产库副本**跑真实升级：迁移到 v20、账目补回 1615 行、`pragma integrity_check` ok、外键为空。真实进程端到端 20 项全过，含「用完 429 → 连试 5 次仍 429 → 删 Key → 同组新 Key 仍 429 → 调大限额立即恢复」。

**注意**

周期到期（到达 `period_limit_start + period_limit_days`）后仍按既有语义交给周限额；这一条没有改动。

## v0.7.1 — 周期额度用满后不再「从 0 重新计」，改为硬停

**当时存在的问题**

阶段 B 的 `periodQuotaTransition` 会在周期 Token/金额用满时返回「用满那一刻」，调用方据此把周窗口起点挪到该时刻。结果是：用量显示归零、周限额从交接点重新累计、后续请求继续放行 —— 运维看到的是「额度明明用满了，服务却没有关闭」。这被当作设计写进了交接文档（v0.6.1 的已知行为），但与实际预期相反。

**改了什么**

- `periodQuotaTransition` 改成 `periodWindowUsage`：只统计当前周期窗口内的真实用量，不再计算/返回交接点。
- `ReserveRequest` 在周期生效时直接用 `overdrawn` / `overdrawnAmount` 判定：用满即返回 **429**（`token_quota_exceeded` / `amount_quota_exceeded`，`scope=period` 带数字），不再改 `weekStart`、不再把周窗口起点挪到交接点。沿用「欠费即拒」口径：调大限额后下一次请求立即恢复，不是永久锁死。
- `GroupOverview` 去掉交接逻辑：周期卡片始终显示当前周期的累计用量（用满后不会归零）；`period.transition_utc` 保留字段兼容前端，恒为空串。周期到期后仍按既有语义交给周限额。
- 管理台额度弹窗/卡片文案、README、`docs/admin-api.md`、交接文档同步改为「用满即关闭服务」。
- 测试改写：原来钉住「用满交接周窗口」的 4 个用例改为钉住「用满 429 + 概览用量不归零 + 调大限额恢复 + 其它分组不受影响」；周期到期交接周的用例保持不变。

**验证**

`go build` / `go vet` / `go test -count=1 ./...` 全绿；真实进程端到端（隔离目录）复现：周期限额压到首笔即用满 → 第二笔 429 `scope=period`，管理台周期用量保持真实累计值、不再归零。

**注意**

- 无数据库迁移、无配置变更；回滚只需把 `.env` 版本改回 `v0.7.0`。
- 另一个口径风险（本次未改）：删除客户端 Key 会按外键级联清掉 `key_reservations`，所有窗口用量随之归零（`requests` 历史行保留）。要彻底消除「删 Key 也能重置额度」，需把额度统计改为基于 `requests` 表或改外键为 `ON DELETE SET NULL`，属架构级改动，需另行确认。

## v0.6.0 — 控制台必须登录，密钥主体只看自己那组（阶段 C）

**当时存在的问题**

管理台是个「匿名只读」页面：任何人打开 `/admin/` 就能看到全站概览、所有供应商、所有分组、
用量分析。分组与额度分片做完了，这层却还敞着——分片在「谁能看」这件事上等于没做。
老板的原话：「先让用户输密钥，输入了密钥才能看到对应分组信息，而目前是谁都能看到」。
另一件事是角度问题：概览只有全站数字，想看某个组必须绕到模型组页面点「概览」弹窗。

**改了什么**

- **没有任何匿名路径**。`/admin/api/` 一律先认人：管理员用 `X-Admin-Key`，分发出去的客户端密钥
  用 `Authorization: Bearer crk_…`。登录框自动判别两种密钥，`app_…` 应用型标识显式拒绝
  （它的明文创建时即丢弃，无可验证物）。
- **密钥主体是只读且按分组裁剪的**：能看自己那组的概览、额度、渠道（不含上游地址）、授权模型、
  自己的请求明细与「我的用量」；看不到别的组、别的密钥、运行配置、插件，也做不了任何写操作。
  跨组一律 404 而非 403——组 ID 是自增整数，403 等于确认它存在。
- **概览页保留全站数据，另加「统计范围」下拉**：全部分组看全站；选一个组则看到该组四个窗口的
  额度卡片、本组 RPM、进行中、成功率，最近请求也随之切到该组。用量分析的筛选条件里同样加了分组。
- 四种登录拒绝分开返回：`authentication_required` / `invalid_api_key` / `token_expired` /
  `console_login_not_supported`，前端各自出文案——过期该续期，无效该换凭据，别让用户瞎试。
- 新增 `GET /admin/api/me`（自己这把密钥的用量、限额、有效期、可用模型数），概览页的
  「我的用量」直接复用。

**注意**：这是**破坏性变更**。任何脚本若依赖「不带凭据也能读 `/admin/api/overview`」，
升级后都会拿到 401。

## v0.5.0 — 额度从全局搬进每个分组

**当时存在的问题**

全局额度（`relay.env` 里的 `TOKEN_LIMIT_*` / `AMOUNT_LIMIT_*` / `PERIOD_LIMIT_*`）是**整个网关共用一份**。
但分组已经是「一个团队 / 一个软件一条通道」的单位，共用一份额度意味着：A 组把今日用量打满，
B 组的客户端全部 429；想让内部组宽松、外包组收紧，只能靠 Key 级总额度勉强凑，而 Key 额度是
**累计不轮换**的，对「每天 5 元」这种需求完全不对路。分组概览也一直按「走组内渠道的请求」统计，
与额度扣减的口径（按账目行归属）不是一回事，两边数字对不上时无从判断谁对。

**改了什么**

- 迁移 v18：`model_groups` 加 10 列（4 窗口 × Token/金额 + 周期长度 + 周期起点），全部可空，
  `NULL` 或 `0` = 不限。**升级不会让任何分组突然被限额**（不设就是不限）。
- 判定改为在预留事务内**从密钥所属分组那一行**读额度，改完下一次请求即生效；`QuotaLimits`
  保留原字段但语义从「全局配置快照」变成「本次请求生效的额度」，五个窗口判定函数逻辑一行未改。
- 启动播种：`relay.env` 里残留的全局额度会被灌进**每个现有分组**（只填还没设过的列），
  然后从文件里删键；删键本身就是幂等标记。日志 `全局额度配置已灌入 N 个分组并从 relay.env 移除`。
- 管理台：概览摘掉四张全局额度卡（全局视图已经没有限额可展示）；模型组列表加「额度」列
  （三个主窗口最紧张的那个占比，≥80% 黄、用满标红「已欠费」）；组编辑弹窗加 9 个额度输入框
  （`0 = 不限；留空 = 保持原值`，金额按元进出、库里存微元）；组概览弹窗用四张额度卡展示
  「已用 / 本组限额」，口径说明改为「仅计入归属本组的请求」；删组确认写明将解绑多少把密钥。
- 顺手补掉阶段 A 的两处欠账：密钥编辑弹窗里**当前分组即使停用也显示**（标「已停用」），
  且只在选中值真的变化时才 `PUT /group`（避免「只改名字却静默解绑」和停用组的 400）；
  首次启动日志区分「首启」与「恢复既有凭据」两种文案。

**踩过的坑**

| # | 坑 | 后果 / 修法 |
|---|---|---|
| 1 | 周期起点自动填的是**秒级** RFC3339（`…48Z`），账目行是 RFC3339Nano（`…48.219Z`）；SQL 里按**文本**比较，`48Z > 48.219Z` | 同一秒内写入的账目被整段排除在周期窗口外，**周期额度静默失效**（永远 0 用量、永不拒绝）。窗口边界全部改 `julianday()` 数值比较 |
| 2 | 播种时把「没设」写成 `0`、金额用 `ParseInt` 读 | 前者会让所有分组从 NULL 变 `0`（语义上仍是「不限」，但丢掉了「未设」），后者把 `12.5` 截成 `12`。改为 `COALESCE(col, NULLIF(?, 0))` + `ParseFloat × 1e6` |
| 3 | `config.Store.Write` 会把未知键**合并**回文件 | 用它在播种后删键等于没删（下次启动又灌一遍）。新增 `WriteMapping`（不合并）专用于此处 |
| 4 | 前端把 `TensionPct == 0` 一律渲染成「不限」 | `0` 有两种含义：没设限额 / 设了但一点没用。必须看 Token 三列本身，否则刚设完额度的组还显示「不限」，运维以为没生效 |
| 5 | 自定义周期**只填天数不填周期限额**不生效（既有语义，`periodActive` 要求至少一项周期限额） | 界面上原本没说，运维填完 3 天以为已生效。编辑弹窗里写明「要同时填周期长度与至少一项周期限额」 |

**BREAKING CHANGE**：`TOKEN_LIMIT_5H` / `TOKEN_LIMIT_DAILY` / `TOKEN_LIMIT_WEEKLY` /
`TOKEN_LIMIT_PERIOD` / `AMOUNT_LIMIT_5H` / `AMOUNT_LIMIT_DAILY` / `AMOUNT_LIMIT_WEEKLY` /
`AMOUNT_LIMIT_PERIOD` / `PERIOD_LIMIT_DAYS` / `PERIOD_LIMIT_START` 不再从 `relay.env` 读取。
`GET /admin/api/overview` 也不再返回 `five_hour` / `daily` / `weekly` / `period` 四个窗口
（改看 `GET /admin/api/groups/{id}/overview`）。旧部署升级后额度会自动搬进各分组，行为不变。

**已知但尚未实现**

- `_e2e/run_e2e.py` 的 39 项断言里「额度对照实验」依赖已删除的全局额度配置接口，本版本后**必然失效**。
  本机没装 Python 跑不了，也不做盲改——待装好 Python 后改为「按分组设额度 + 断言 429 带分组名」重跑。
- 金额展示仍有历史遗留的 `¥12.500000` 形态（`fmtYuan` 对非整元的 6 位小数尾部零只剥 3 个）。
  属全局金额格式，改动会波及请求日志与用量分析，留待单独处理。

## v0.3.7 — 修复「流式对话突然中断」（线上故障）

**当时存在的问题**

| # | 问题 | 后果 |
|---|---|---|
| 1 | 上游 HTTP 客户端设了 `http.Client.Timeout = connect+read+write`（默认 **340 秒**）。这是**整个请求的总超时，包含读取响应体的全部时间** | 任何超过 340 秒的流式回答被**无声掐断**。记录里只留 `upstream_status=200` + **零 token** 的 `failed`，从管理台完全看不出是超时 |
| 2 | `MAX_STREAM_DURATION`（默认 30 分钟，管理台可配）**从未作用到请求上**，只被后台回收循环当作「陈旧预留」的阈值 | 管理台显示 30 分钟、实际生效 340 秒，两个数字互相矛盾且无人能察觉 |
| 3 | `UPSTREAM_*_TIMEOUT` 改了需要**重启容器**才生效（启动时按值交给 Registry），但 `RestartOnlyChanges` 只列了 `HOST`/`PORT`/`DB_PATH` | 管理台显示「已即时生效」，运维据此以为调大了超时——排查时最容易走错的一步 |

**修复**

- 上游客户端**不设总超时**，职责拆开：「上游不响应」→ `UPSTREAM_READ_TIMEOUT`（`ResponseHeaderTimeout = connect + read`）；「流跑多久」→ `MAX_STREAM_DURATION`（relay 层用 context 施加，**0 = 不限**）；「客户端断开」→ 请求自身 context。
- `MAX_STREAM_DURATION` 现在真的生效，且**热生效**；cancel 绑到 `response.Body.Close()`（调用方本来就会 defer，不会漏 timer）；失败分支用原始 ctx 结算，避免 ctx 已超时导致落库失败。
- `UPSTREAM_CONNECT/READ/WRITE/POOL_TIMEOUT` 四项加入 `RestartOnlyChanges`，管理台会明确提示需重启。

## v0.3.6 — 应用型凭据（客户端里没有密钥）

**当时存在的问题**：客户端**必须持有 `crk_` 密钥**。而写进客户端里的任何秘密迟早会被提取 —— 用户能把密钥带去别的软件里用。

**修复**：`keyless: true` 创建**应用型凭据**，服务端生成公开的应用标识（`app_…`）并**丢弃密钥明文**（不返回、不落盘），客户端只用请求头 `X-App-Id` 接入。两套认证**互不越界**（密钥型的 `public_id` 为空，应用型无法用 Bearer），同给时密钥优先、失败回落应用标识。

> ⚠️ 边界：应用标识是**公开的**，能访问到网关的人都能调用 —— 真正的门是「谁能访问到网关」（内网/防火墙/反代），因此必须配并发与额度上限。跨不可信网络的正确做法是让客户端连**你自己的中转服务**。

**踩过的坑**：创建应用型凭据时先清空 token 再算摘要 → 所有记录得到同一个「空串 HMAC」→ 撞 `token_digest` 的 UNIQUE 约束。必须**先算摘要再丢弃明文**。

## v0.3.5 — 短时令牌（客户端凭据会自己过期）

**当时存在的问题**：客户端 Key **永久有效**，只有手动停用/删除/重置才失效。凭据泄露后除非有人发现并吊销，否则一直可用。

**修复**：`client_keys.expires_at_utc`（`NULL` = 永久，**历史 Key 不受影响**）。创建/编辑可设 `ttl_seconds`（**三态**：缺省 = 不动、`0` = 改永久、`>0` = 从现在起重新计时即续期）。过期返回 **401 `token_expired`**（与 `invalid_api_key` 分开，客户端才知道该换令牌而不是当服务故障重试）。管理台显示剩余寿命（不足 24 小时标黄、过期标红）。

> 「留空不改有效期」这条必须守住，否则「重命名」会变成静默的永久续期 —— 已由 `admin_test.go::TestAdminKeyTTLThreeStates` 钉住。

## v0.3.4 — 客户端接入信息

**当时存在的问题**：明文密钥只在创建/重置时返回一次，Base URL 与模型名又分散在配置页和模型页，运维要自己拼 —— 拼错的表现是客户端 400/404，从错误信息里看不出是「填错了」还是「服务坏了」。

## 已知但尚未实现

- **客户端指定分组**：现在分组由服务端按凭据绑定决定，客户端不能选。要做需加「请求头指定分组 + 校验在该凭据已绑定的范围内」。
- **客户端自助换令牌**：短时令牌到期需管理员续期。若要客户端自己换，需要一层「用旧令牌换新令牌」的接口，并限定「仅临近过期时可换一次」。
- **公共接口的 CORS**：当前不带 `Access-Control-*` 头（`OPTIONS` 返回 405），网页类客户端**不能跨源直连**，必须走同源反向代理。要支持需显式加 CORS，但那会让 relay 对任意网页开放（浏览器里密钥明文可见），只在完全可信环境才建议。
